# Governance and PR flow

Last updated: 2026-06-09.

The living wiki has no server, nor an approval queue of its own: the **gate** is the
Git pull request. The underlying rule is simple and has a strong consequence:

- `main` **is the approved wiki**. Everything in `main` has been reviewed by a
  human and can be cited as operational truth.
- `wiki/<theme>` branches **are proposals**. A branch is a living draft until
  the PR is reviewed and merged; before that, nothing in it counts as approved.

The deterministic code (CI/audit) guarantees what is mechanical — links, secrets,
tests, cockpit freshness. It does **not** guarantee that the idea is correct. That part
belongs to the human reviewer. This page describes where the machine stops and the
person begins.

Method references for this page: the gate rule in
[git-approvals.md](../git-approvals.md), the contract in
[operational-wiki-contract.md](../operational-wiki-contract.md), the ingestion process
in [ingestion-process.md](../ingestion-process.md) and the mechanical check

## main approved, wiki/<theme> branch proposed

The flow of a proposal is linear and has named states (created, compiling,
ready for review, awaiting the human gate, approved/published, or
superseded/rejected/archived). The complete state machine lives in
[git-approvals.md](../git-approvals.md); what matters here is the life cycle
seen by governance:

1. A branch is created from `main` with the tool-neutral prefix.
2. The author (human or agent) compiles manifests, events, pages and the diff.
3. The local validations run (audit, coverage, cockpit freshness).
4. The PR is opened; a human reviews the **content**, not just the file list.
5. Only then does the merge into `main` occur.

A second branch is not opened for the same page when a proposal is already
open: the existing branch is updated, rebased against `main` and old
proposals are marked as `superseded`. This avoids two competing "truths" for
the same page.

## Tool-neutral branch convention

The branch prefix is `wiki/` — deliberately **tool-neutral**. Any
agent (Claude, Codex, Gemini, or a human directly) uses the same convention, without
recording the name of a tool in the branch or in the merge commits. The prefix is
configurable and comes from [wiki.config.yaml](../../../wiki.config.yaml) (`branch_prefix: wiki/`),
not a value hardcoded in the code. Recommended patterns:

- source ingestion: `wiki/ingest-YYYY-MM-DD-<theme>`;
- system adjustment: `wiki/system-<theme>`;
- small fix: `wiki/fix-<theme>`.

The motivation is portability: the methodology should run the same way in the personal repo and in the
open-source version, without tying the history to whoever operated it.

## Human review: what the CI does not see

The model separates **two roles**. The CI validates the mechanical; the human validates the
conceptual. Even when an agent opens the PR, a human needs to mark, in the
[pull_request_template.md](../../../.github/pull_request_template.md), four items
that no script can judge:

- **I read the conceptual diff** — what changes in the wiki's behavior, not just which
  files were touched. A green diff in CI can still be conceptually
  wrong.
- **Privacy checked** — PII only on a private page (allowed in this private
  repo); no access secret (token, cookie, password, individualized link,
  credential) anywhere; if something went public, the public export was
  redacted. The two axes of the data policy are in the
  [operational-wiki-contract.md](../operational-wiki-contract.md).
- **Cockpit recompiled** — if the memory changed, the cockpit
  [operations.md](../../operations.md) was regenerated and the freshness check passed
  green. The cockpit is compiled by [wiki_operation_compile.py](../../../scripts/wiki_operation_compile.py),
  never edited by hand.
- **Honest status** — no claim of "done" without evidence of a
  real artifact/page. This is the anti-overclaim, detailed below.

The separation also appears in the lean reusable checklist in
[pr-checklist.md](../../../docs/references/templates/wiki/pr-checklist.md), and the
summary for the reviewer can be generated by
[wiki_pr_summary.py](../../../scripts/wiki_pr_summary.py).

## Split rule: one PR = one theme

A large PR hides problems and tires the review — and a tired reviewer approves on
autopilot. The rule is direct: **one PR covers a single thematic block**. The practical
alert threshold is ~400 lines of diff **or** ~15 files. Above that, the PR must be
split into chained thematic PRs (commit -> PR -> merge), each validated in
a clean clone, or the author explicitly justifies why the block is indivisible.

The operational consequence is that ingestion integrates update blocks as
sequential thematic PRs, instead of a single monolithic PR: each theme enters,
is reviewed and merges before the next.

## Status across two dimensions: core_status vs operational_status

The most common mistake when declaring progress is to confuse "the code exists" with "the
code is in use". The methodology forces two independent dimensions for every
capability:

- `core_status` — the code is present and tested. Values: absent, partial,
  implemented.
- `operational_status` — the capability is being used in real operation, with
  evidence of a page or artifact. Values: absent, pilot, in_use.

The honesty rule: **"done" requires both dimensions**. Without evidence of
real use, the most that can be claimed is `core_status: implemented` with
`operational_status: pilot`. Code written and tested, but that no one has used in a
real flow, is not "ready" — it is a pilot. This convention feeds directly into the
"Honest status" item of the human review checklist.

## Validation in a clean clone

Every approval validation must be reproducible in a **clean clone** (the same
environment the CI sees), not just on the author's machine. The reason: derived
artifacts and raw data are deliberately unversioned (gitignored), so
the auditor [wiki_audit.py](../../../scripts/wiki_audit.py) tolerates by default links
that point to those absent caches — otherwise, a clean clone would fail
on references that only exist on the writer's machine.

Practical consequences:

- The PR is only really "ready" if the validations pass in a fresh checkout,
  without relying on local caches.
- Links to versioned artifacts need to exist in the repo; links to derived/raw
  caches may point to the original (e.g.: Drive) without breaking the gate.
- A strict local mode exists to, on a real machine, require that even the
  derived artifacts exist — useful to catch a dangling reference before opening the PR.

## Draft vs ready PR

Open as a **draft** whenever there is risk: privacy, sensitive-data
classification, change of a living source, scope doubt or broad
consolidation. Make it **ready for review** only after the local audit passes and the
conceptual diff has been reread. The merge into `main` only happens after the human review of the
complete package — sources, synthesis, risks, validations and pending items — because, once
again, `main` is the approved wiki and everything in it becomes operational truth.
