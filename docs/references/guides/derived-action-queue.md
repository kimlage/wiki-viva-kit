# Derived action queue and consumer migration

The canonical action pages are the queue. `python3 -m scripts.wiki_action_queue`
lists active actions from all configured action collections; `--json` emits the
same inventory for a reader. No shared generated queue is written or committed.
The cockpit action board already reads action pages. A static pending index may
point to the command and board, so its URL remains stable; it must not display
an authored count or claim to contain the live members. The command reads the
checkout being inspected, so fetch or select the intended revision first.

`python3 -m scripts.wiki_action_queue --check --base origin/main` validates
canonical state, required lifecycle support, unique IDs and action inventory,
then compares changed actions with the Git merge base using the canonical
transition-receipt diagnostics. If a pending page exists, the check accepts
only the exact pointer below and its restricted metadata. Every materialized
queue, including a currently correct legacy section, fails closed. Missing Git
data is an error. Run the other consumer audit gates as well. It does not make
concurrent changes to the same action mergeable.

Keep the existing page identity and replace its entire body with this exact
pointer, including the blank line after frontmatter and one final newline (LF
or CRLF). The only permitted frontmatter keys are scalar `page_id`, `page_type`,
`title`, `context`, `visibility`, `updated_at`, `stale_after_days`,
`sources_policy`, `gate`, `sensitive_data_policy`, `owner`, `moc_parent` and
`status`. Remove `collection`, `actions` and other keys from this page; move any
independently useful content to an appropriate separate page. Do not add rows,
counts, lists, free text, or a second section. A marker alone is insufficient.

## Preserving historical consolidation provenance

If immutable ingestion events name the old queue page in `consolidated_into`,
retain their historical content on one regular wiki page and bind it explicitly
in the consumer's `wiki.config.yaml`:

```yaml
action_queue:
  history_page: memories/actions/queue-history.md
```

Use the consumer's configured memory root and an existing repository-relative
Markdown path. The history must be distinct from the pointer and ingestion
events, have valid ordinary frontmatter (not a source or ingestion-event page),
and contain a YAML list of nonempty `source_refs` that intersects the references
of each event. The consolidation audit follows
this binding only for the configured queue page after validating its exact
pointer; missing, unsafe, symlinked or invalid history, an altered pointer, or
a missing per-event source match fails the audit. It does not change historical
events or transfer this exception to other targets. A matching source reference
is traceability evidence, not a substitute for reviewing the historical content.

## Migration in a consumer-owned PR

1. Sync this kit and inspect the C1/C2 plan. In the consumer's C3 migration,
   replace the entire generated body and metadata with the strict pointer and
   allowed identity metadata above. Review any consumers of its old lists or
   body; change them to read actions or the JSON command output.
2. Change the consumer's `wiki_action.py queue --check` entry point to invoke
   `scripts/wiki_action_queue.py --check`, propagating its exit code. Replace
   `queue --write` with the read-only queue command and update instructions,
   tests, hooks and PR gates that formerly required generated bytes. Do not
   run a post-merge commit: that would recreate the shared conflict.
3. Run the new check against the intended merge base. Fix invalid canonical
   action states, duplicate IDs and lifecycle/receipt problems through the
   existing action writer; never fabricate a historical transition. Verify the
   old and new active inventories match before removing the generated list.
   Run consumer gates, review and merge the adoption PR under consumer policy.
4. Each in-flight PR rebases once onto the adoption after it merges, drops its
   generated index change, and validates again. Thereafter independent action
   changes no longer edit a common queue file. The migration does not remove
   conflicts in unrelated shared files or replace the integrator's review.

This chooses a derived queue over a custom merge driver (which cannot be
assumed installed on every host) and fragments (which duplicate action state
and still need a reliable assembled view). A static page in GitHub is a signpost,
not a live server-side rendering; use the CLI or cockpit for the live queue.
