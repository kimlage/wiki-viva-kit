# Derived action queue and consumer migration

The canonical action pages are the queue. `python3 scripts/wiki_action_queue.py`
lists active actions from all configured action collections; `--json` emits the
same inventory for a reader. No shared generated queue is written or committed.
The cockpit action board already reads action pages. A static pending index may
point to the command and board, so its URL remains stable; it must not display
an authored count or claim to contain the live members. The command reads the
checkout being inspected, so fetch or select the intended revision first.

`python3 scripts/wiki_action_queue.py --check --base origin/main` validates
canonical state, required lifecycle support, unique IDs and action inventory,
then compares changed actions with the Git merge base using the canonical
transition-receipt diagnostics. Missing Git data is an error. This validates
actions, not freshness of a generated file. Run the other consumer audit gates
as well. It does not make concurrent changes to the same action mergeable.

## Migration in a consumer-owned PR

1. Sync this kit and inspect the C1/C2 plan. In the consumer's C3 migration,
   replace the generated section of the existing pending index with stable
   instructions linking the command and the action board. Remove generated
   `collection.members` rather than leaving a stale membership list. Retain
   its page identity and navigation links. Review any consumers of that list
   or of its body; change them to read actions or the JSON command output.
2. Change the consumer's `wiki_action.py queue --check` entry point to invoke
   `scripts/wiki_action_queue.py --check`, propagating its exit code. Replace
   `queue --write` with the read-only queue command and update instructions,
   tests, hooks and PR gates that formerly required generated bytes. Do not
   run a post-merge commit: that would recreate the shared conflict.
3. Run the new check against the intended merge base. Fix invalid canonical
   action states, duplicate IDs and lifecycle/receipt problems through the
   existing action writer; never fabricate a historical transition. Verify the
   old and new active inventories match before removing the generated list.
   Run consumer gates, review and merge the adoption PR under consumer policy.
4. Each in-flight PR rebases once onto the adoption after it merges, drops its
   generated index change, and validates again. Thereafter independent action
   changes no longer edit a common queue file. The migration does not remove
   conflicts in unrelated shared files or replace the integrator's review.

This chooses a derived queue over a custom merge driver (which cannot be
assumed installed on every host) and fragments (which duplicate action state
and still need a reliable assembled view). A static page in GitHub is a signpost,
not a live server-side rendering; use the CLI or cockpit for the live queue.
