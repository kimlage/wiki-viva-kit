# Reviewing software changes under living wiki rules

Read the affected code, current operating rules and the complete diff. Keep
source dates and financial or personal facts unchanged during technical work.
Record actual commands, results, unresolved failures and the exact reviewed SHA
in the PR. Applicable privacy, authority and publication limits still govern.

Use [scoped freshness](../freshness-impact.md) for actual changed assertions and
their dependencies. A short, independently reviewed documentary-only path and
rationale can distinguish a spelling, navigation or catalogue edit from a new
factual claim. It never exempts a dependency reached from another factual seed.
Do not raise freshness budgets, renew dates or repeatedly alter the last
reported dependency simply to obtain a passing check.

Adopt shared changes through the [normal sync workflow](../../../AGENTS.md#upgrades-and-releases).
Review B0, copy the committed runtime, apply explicit consumer migration and
validate the consumer. Source facts stay with their canonical documents; code
correctness stays with tests and review. Neither creates authority or proves
that the running service adopted the change.
