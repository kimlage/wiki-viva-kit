# Software changes under living wiki rules

The existing [document_record.v1 contract](../freshness-impact.md#explicit-documentary-records)
can describe a software log/catalogue addition governed by living rules without
making every historical subject of those rules a current factual premise.
This is an authored, reviewed declaration for one exact base/candidate pair.
It does not change the evaluator or automatically classify a consumer wiki.

## Review the complete causal frontier

Read the changed records, shared introductions/frontmatter and all applicable
rule sections before qualifying individual occurrences. A shortest reported
path is only one witness: fixing its final edge does not establish closure.
Prepare one complete semantic plan, then evaluate its actual result.

| Reference in a software change | Existing v1 treatment, when supported by its literal meaning |
| --- | --- |
| Applicable approval, procedure, audit or operating rule | Consume the canonical H2 record and all necessary `context_records`, retaining its page date/cadence. |
| An actual prerequisite fact or current business assertion | Keep factual consumption and its transitive prerequisites. |
| A dated subject or origin of a rule | An exact `provenance` occurrence with verified historical evidence; retain the living rule separately. |
| A log, proposal or impact ledger where a result must be recorded | An exact `change_target` occurrence; it does not assert that recording or validation succeeded. |
| A link-format example or product identity | An exact `navigation` occurrence only if it makes no factual assertion about the destination's current state. |
| A new implementation claim | Verified candidate implementation evidence, without retroactively placing that implementation in the base. |
| An ambiguous reference, second factual citation or unreviewed occurrence | Conservative whole-document consumption. |

Partitioning alone does not qualify old links. A procedure's log destination
and two separate audit-ledger destinations require six exact bindings when
they exist in both snapshots. Do not omit the procedure or audit section to
avoid its references. Do not classify all links to the same endpoint together.

## Keep rules and evidence distinct

Select real, unique top-level H2 sections using byte-hashed selectors. Include
supporting limits, checklist and validation sections through `context_records`;
preserve nested H3 content. A title resembling a heading inside frontmatter is
not a selector. Shared introduction and factual metadata are inherited and need
the same complete review as body references.

Canonical permission and its exclusions stay live: a historical capture cannot
renew, replace or broaden authority. Account, payment, credential, publication
and external-action limits remain applicable. Implementation evidence proves
technical behavior, not permission. An actual policy or prerequisite change
must still reach existing consumers; discovering an unchanged shared rule as a
prerequisite does not fan out to its other consumers.

Examples, recording destinations and conditional source requirements do not
assert that every destination is current. Their actual obligations remain:
run the required integrity/privacy/source/impact checks, close real impact,
record results and honor promotion policy. If a change makes a real financial
claim, its financial source is a prerequisite even when another occurrence of
that source is historical. A role never proves a gate passed or grants access.

Immutable evidence proves captured bytes or events at the declared cut. Bind
each relevant origin separately and keep actual technical prerequisites in the
candidate. Adding implementation evidence does not implicitly remove inherited
historical sources. Do not renew old source dates, copy private consumer pages
into public fixtures, raise a budget or add exemptions to obtain a passing gate.

## Consumer adoption

Use the [normal B0/C1/C2/C3 workflow](../../../AGENTS.md#upgrades-and-releases).
The consumer owns its exact records, role rationales, evidence, complete input
maps and privacy boundary. Review the full C3 plan before applying it; update
hashes only after renewed semantic review. Other consumers and undeclared
occurrences retain conservative semantics.

Run the actual consumer audit against the agreed exact base and review alternate
dependency paths too. Public synthetic success is not consumer closure,
promotion, a successful callback or a served deployment. If an inseparable H2
mixes live factual requirements with historical context, v1 must retain the
factual dependency; this guide does not authorize discarding it or inventing a
narrower selector.

The [composite synthetic regression](../../../tests/test_software_change_records.py)
covers two new software records, inherited catalogue metadata/introduction,
canonical approval and source limits, procedure contexts, nested audit checks,
operating rules, historical origins, six old recording destinations and actual
implementation evidence. Negative controls retain stale canonical rules and
facts, body/metadata financial claims, missing qualifications, real-change
propagation and refusal of a changed canonical snapshot. This fixture verifies
only its declared synthetic case.

## Authoring the complete consumption frontier

Use [wiki_page_graph.py](../../../scripts/wiki_page_graph.py) to inspect the
configured exact snapshot pair without evaluating freshness or inferring roles:

```sh
python3 scripts/wiki_page_graph.py --record-review --target memories/coordination.md \
  --target memories/system/log.md --out /private/new-record-review.json
```

Use the consumer's actual paths. The command reads `audit.freshness_base` and
`audit.freshness_records`; it has no base/contract override or apply option.
It refuses existing output files, invalid snapshots/bindings and changing inputs.
The output includes complete source text at the frontier: retain it privately.

The same `project_records` loop supplies raw occurrence digests, both origins,
every inherited consumer variant, existing bindings and actual projected edges.
The census includes all incoming occurrences and own premises of the requested
documents, plus every other authored page changed in that transaction. Second
links, factual metadata and relations authored on another page remain distinct.
It is not a list of selected shortest-path witnesses. Input maps, variant counts
and a checksum bind what was enumerated; they do not prove semantic approval.

Read the assertion and its necessary context before authoring each v1 binding.
An absent binding stays WHOLE; a declared invalid binding fails closed. A valid
contract alone does not prove the author's review is complete. Unknown, LIVE,
temporal and identity assertions must retain their actual support. For example,
an appended account revocation must still reach a consumer asserting current
authorization, even if the source's earlier prefix is unchanged. A statement
explicitly limited to an earlier cut can consume its proven historical support.
Neither append-only preservation nor a new record date supplies that intention.

## A new transaction using v1

A v1 declaration describes one exact pair, not a permanent frozen diff base.
For a later proposal, preserve the historical contract unchanged and author a
new file for the approved parent and final candidate. The approved parent's
CURRENT view can supply the initial BASE semantics only after checking the
parent's bytes, occurrences, selectors, inherited context and evidence. Do not
copy the earlier BASE bindings blindly. Re-key an identity only when its content
and consumption are equivalent; hashes do not establish semantic intent.

The new complete BASE/CURRENT maps and origin-specific artifact/record hashes
must match their snapshots. Keep dates, cadence, normative premises and unknown
WHOLE consumers. Removed or retargeted dependencies in this transaction still
participate from BASE; new candidate evidence cannot be placed in the parent.
Change the configured pointer/base only through the reviewed consumer C3, with
the normal integrity, privacy, impact and freshness gates. An unchanged stale
page is still blocking when actually required, or under applicable global
maintenance; making a new pair does not renew it or waive its dependencies.

This authoring tool does not replace the separate direct-impact check or its
reasoned acknowledgments. Review the entire final package before application,
then validate it normally. No report, checksum or role grants access or proves
that the integration passed.
